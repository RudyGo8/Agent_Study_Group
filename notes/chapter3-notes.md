# 第三章学习笔记：用户记忆和知识库

## 1. 总结

- **两个尺度，同一个问题**：用户记忆让 Agent 成为"懂你的助手"（个体），知识库让 Agent 成为"领域专家"（群体）——共用底层技术：向量检索、知识压缩；同面临麻烦：信息冲突、知识过期、检索不准
- **先立标尺再做设计**：三层次评估框架——基础回忆、多会话检索、主动服务，逐层递进；后文所有记忆技术都用这把尺子衡量
- **四种存储格式按粒度递进**：Simple Notes 最小事实 O(1) 但丢关联；Enhanced Notes 完整段落但冗余；JSON Cards 三层嵌套可部分更新但强制分类；Advanced JSON Cards 加 backstory、person、relationship、时间戳解决消歧——"张医生"是我的牙医还是父亲的心脏科医生，脱离情境无法理解。选择标准：关键且少量用 Advanced JSON Cards，大量非关键用 Simple Notes，生产多为混合
- **记忆生命周期**：读取相关记忆 → 后台提取候选 → 来源与策略核验 → 更新；写入不能跳过来源、时间、冲突、隐私四项检查
- **RAG 主流水线**：分块 → 稠密检索 → 稀疏检索 → 融合 → 重排序 → 生成，用 recall@k 等指标验收
- **稠密与稀疏互补**：稠密嵌入抓语义相似，kitty 对 feline/cat；稀疏 BM25 抓精确名称、代码、多语言；没有单一策略全场景可靠，混合加神经重排序才是生产级
- **结构化索引按需投入**：RAPTOR 树状跨层穿梭，适合从概念钻进细节；GraphRAG 图谱关系漫游，适合 A 与 B 什么关系；只在需要跨文档综合或多层导航时才值得，代价是索引和查询都要更多 LLM 调用
- **文件系统范式（OpenViking）**：知识组织第三哲学——所有上下文映射为 viking:// 虚拟文件系统，L0 摘要约 100 token、L1 概览约 2000 token、L2 全文三层按需加载，与 Skills 渐进披露如出一辙；Markdown 纯文本让知识可直接读、可 git 回滚；关键前提是文件间必须建立 Wikipedia 式链接与索引，否则知识成孤岛，越多越难检索
- **智能体化 RAG**：从被动管道到主动探索者——分解问题、并行检索、评估缺口、二次检索、综合回答；简单问题传统 RAG 更快，复杂多跳问题 Agentic 显著占优
- **上下文感知检索**：给每个分块生成上下文前缀当身份标签——结合 BM25 检索失败率降 49%，再加重排序降 67%；索引成本靠 prompt cache 压到约每百万文档 token 1 美元
- **双层记忆架构（本章汇合点）**：Advanced JSON Cards 常驻上下文给全局概览 + 上下文感知检索按需取原始细节——只靠常驻丢细节、只靠检索缺全局，两者叠加才让第三层主动服务首次工程落地
- **知识更新两节奏**：增量更新把知识库当代码库——每次变更是一个 PR，走提议者—审核者闭环，Proposer 只写工作分支、Reviewer 只读证据、只有合并流程动主库，超迭代上限转人工；定期整理回到原始数据去重合并、冲突做场景限定而非取舍，diff 经异源 Reviewer 审核才发布。三层分离：原始证据层只增不改、知识层持续修订、服务层索引是可重建的派生物
- **隐私保护本地化**：日志脱敏用本地小模型而非云端——敏感日志发出去脱敏本身就违背初衷
- 全书定位：本章建第 1 章循环中的提案段——把一条证据变成最小、可审查、可回滚的修改；第 9 章把同一基础设施用于行为经验

## 2. 实验

**3.1 用三层次框架评估记忆系统**
论证 先立标尺——三层各 20 个用例、跨会话约 50 轮沟通，记忆生成后用 LLM-as-a-judge 对照参考答案打分，后面所有记忆技术都用这套评估集

**3.2 记忆策略对比**
论证 四种格式的取舍在数据上兑现——Simple Notes 最低成本过第一层，但综合与消歧的二三层频繁失分；Advanced JSON Cards 消歧和跨会话关联最好，代价是维护调用更贵更慢

**3.3 本地模型智能日志脱敏**
论证 隐私保护要本地化——Ollama 跑 0.6B 小模型做 PII 检测，召回 95% 以上且假阳性远低于正则；超高吞吐用正则粗滤加 LLM 深析的混合

**3.4 向量检索 ANN 索引对比**
论证 海量向量靠近似最近邻——ANNOY 与 HNSW 两种后端可切换，直接观察两类主流 ANN 算法的实践差异

**3.5 从零实现 BM25**
论证 稀疏检索机制完全透明——分词去停用词、构建倒排索引、TF/IDF 计算逐步可查可手算复现，教育价值大于性能

**3.6 混合检索流水线**
论证 没有哪种单一检索策略全场景可靠——语义相似、精确名称、多语言、代码各有胜负；神经重排序把被单一方法低估的文档提上来，稠密加稀疏加重排才是生产级做法

**3.7 结构化索引：RAPTOR 与 GraphRAG（三星）**
论证 两种知识组织哲学——RAPTOR 跨层穿梭，先在高层摘要定位 SIMD 再向下钻到 SSE 叶子，适合概念到细节；GraphRAG 关系网漫游，SSE 实体遍历到 XMM 寄存器、浮点运算，适合关系性问题；组合优于单选

**3.8 智能体化 RAG 对比**
论证 从回答问题到解决问题——简单法条问题传统 RAG 单次检索更快；复杂量刑问题 Agentic 分解并行检索、评估缺口、二次聚焦检索，多跳准确率显著提升，代价是响应速度

**3.9 智能体化 RAG 构建用户记忆**
论证 对话历史本身当知识库——search_user_memory 工具多轮检索，两辆车的案例先搜本田再发现线索二次搜特斯拉；但孤立分块在矛盾转账指令上失败——三个各自独立的修改无法判断哪个最终有效

**3.10 上下文感知检索**
论证 给分块加身份标签——无上下文库查"ACME 收入增长"命中一堆噪声，有上下文库精确引导；失败率降 49%、加重排 67%，成本靠 prompt cache 可控

**3.11 上下文感知检索增强用户记忆（三星）**
论证 双层记忆架构落地——上下文前缀让三个矛盾转账块带上谁在什么意图下修改的线索，冲突可判定；JSON Cards 常驻护照事实加按需检索机票细节，识别一月机票与二月护照过期的隐藏关联，主动建议加急续签——第三层主动服务首次工程实现

**3.12 司法判例知识提取（三星）**
论证 知识库不必是静态仓库——自下而上因子发现替代人类先验模式，聚类找出案件原型如轻微口角徒手斗殴致轻伤，构建因子重要性层次模型驱动对话式按重要性提问——Agent 先读懂数据、提炼决策逻辑，再基于逻辑回答

## 3. 思考题

**1. 在用户记忆系统中，当同一用户在不同会话中提供了矛盾信息（比如两次提到不同的家庭住址），记忆系统应该如何处理这种冲突？**

Answer:
冲突既不能悄悄覆盖，也不能并存着猜一个。
- 写入时核验：新信息带来源和时间戳，默认新信息覆盖旧值，但旧值进历史不删除——留审计线索。
- 结构上支持：Advanced JSON Cards 的 backstory、person、时间戳正是为此设计；实验 3-11 的转账案例靠"谁在什么意图下改的"判定最终有效。
- 不确定时澄清：时间顺序不明或来源冲突，把两条都摆出来问用户，而不是自行选一条。
- 读取时防御：检索到多条矛盾记录时，把冲突如实呈现并请用户确认，绝不静默择一。

**2. 上下文感知检索将原始文档的上下文附加到每个分块。但如果原始文档本身结构混乱或存在矛盾信息，这种方法可能传播甚至放大错误。你会如何在检索阶段引入"信息质量"信号？**

Answer:
给分块附加质量元数据，让质量参与排序。
- 索引阶段：生成上下文前缀时顺带做一致性检测——与库内已有事实矛盾的块打上冲突标记；来源权威度、时效性一并入元数据。
- 检索阶段：最终分数 = 相关性 × 质量权重，权威新源压过过时旧源。
- 冲突成对召回：命中矛盾内容时把分歧双方一起返回并标注"存在不一致"，让模型呈现分歧而非默默取一。
- 治本在写入端：源头文档的矛盾应该在知识更新的核验环节拦下，检索端的质量信号是最后防线不是第一道。

**3. 多模态信息提取会先把图表转为文本描述再检索，这个"翻译"过程可能丢失视觉信息中的空间关系。举一个具体例子，说明纯文本描述无法完整传达的图表信息，并设计一种保留该信息的方案。**

Answer:
例子：建筑平面图。"厨房在客厅西侧、走廊连接两者"这类描述能列出来，但"从大门走到厨房不经过卧室的最短路径"需要拓扑与几何联合推理——纯文本把二维布局压成一维句子，空间关系必然损耗。
保留方案：
- 原图保留加结构化伴生：文本描述用于检索命中，命中后调多模态能力读原图做空间推理。
- 结构化矢量数据：平面图存房间邻接表和坐标 JSON，查询交给程序化最短路计算，文本只做索引。
- 本质：文本负责"找到"，空间关系交给保留拓扑的表示去"回答"。

**4. Rich Sutton 的"苦涩的教训"认为通用方法（搜索和学习）最终会胜过手工设计的特征。本章构建的整个知识系统（分块策略、索引结构、检索管道）是否本身就是一种"手工设计"？如果模型能力足够强，这些设计是否会被简单的"全量输入"所替代？**

Answer:
承认是手工设计，但对手不是"全量输入"。
- 全量输入撞三堵墙：上下文窗口有限；缓存读取随轮数二次方增长；第 2 章的结论——上下文学习本质是检索而非推理，信息越多反而检索命中率越低。
- 苦涩教训的正确打开方式是"边界移动"而非"设计消失"：模型变强，分块、混合检索这些手工件会被模型原生能力逐步吸收，就像 CoT 咒语被思考模式内化——第 1 章思考题 10 的规律在这里重演。
- 但治理责任不灭："写什么、信什么来源、何时更新、冲突怎么办"这四件事，模型再强也是 Harness 的责任，只是手段从分块策略升级为更上层的知识治理。

**5. 随着模型能力的提升，你认为领域知识库还重要吗？未来强大的基座模型是否有可能包含领域知识库中所有的信息，从而不再需要领域知识库？**

Answer:
会缩小，不会消失——三条硬边界模型跨不过去。
- 私有性：企业内部流程、用户个人数据，模型训练时永远看不到——这是数据权属问题不是能力问题。
- 时效性：训练截止之后的一切。实验 1-2 东盟成员国那道题就是现场证明——模型的"记忆"会过期，知识库的更新是实时的。
- 责任性：领域应用要可审计、可引用、可回滚——参数里的知识做不到这三样，你没法"审计"一个权重，也没法对它做 diff。
- 分工结论：基座模型内化公共、静态、成熟的知识；知识库管私有、新鲜、需负责任的知识。两者是分工不是替代。

**6. RAPTOR 通过自底向上的层次摘要构建树形索引，GraphRAG 通过实体关系构建图结构索引。这两种结构化索引分别擅长回答什么类型的查询？**

Answer:
- RAPTOR 擅长"从概念逐步钻进细节"：先在高层摘要定位 SIMD 宏观概念，再沿树向下钻到 SSE 叶子节点的技术细节——多层次导航类查询。
- GraphRAG 擅长"A 和 B 之间是什么关系"：定位 SSE 实体后遍历关系边到 XMM 寄存器、浮点运算、社区分析给出架构位置——关系性、多实体关联类查询。
- 判断标准：要跨文档综合或多层下钻才上结构化索引，普通"找到含某信息的片段"用混合检索就够——结构化索引的索引和查询都要更多 LLM 调用，是花得起的场景才用。

**7. 文件系统范式将知识组织为类似文件系统的层次结构。这种方式和传统的向量数据库 RAG 相比，在什么场景下更有优势？**

Answer:
知识天然有层次和命名空间时占优——代码库、文档站、组织制度。书里三个机制是核心：
- L0/L1/L2 三层按需加载：摘要约 100 token 常驻、概览约 2000 token 供规划、全文仅在深入时加载——无关的在 L0 就被剪掉，token 花在刀刃上，与 Skills 渐进披露如出一辙。
- Markdown 纯文本而非专用数据库：人类可直接阅读编辑、git 管版本可回滚、Agent 用 write_file 在工作分支自主记录再走审核合入——写入可审查、可回滚。
- 隐形前提——文件间必须建链接：像 Wikipedia 一样条目互链加索引页，Agent 才能顺链接导航；只平铺文件不建链，知识越多越难检索，反而不如向量库。且不同模型主动建链的意愿差异大，写入提示词必须明确要求。
- 向量库的领地：海量、扁平、语义模糊匹配，如十万条客服记录找相似案例。两者可叠加：文件系统做组织骨架，向量索引做检索加速。

**8. 从结构化数据（如司法判决数据库）中自动发现"裁判因素"和"因素重要性层级"，本质上是让 Agent 从数据中归纳规则。这种数据驱动的知识提取是否能达到人类专家手工编写规则的质量？**

Answer:
各有胜场，当前是互补不是替代。
- 数据驱动强在：无人类先验偏见，因子从数据自下而上长出来；覆盖长尾——专家规则管常见案，聚类能发现预谋团伙斗殴致重伤这类原型；重要性有统计依据；随数据更新。
- 数据驱动弱在：数据的偏差直接变成规则的偏差；小样本罪名不可靠；只学得相关学不到因果；做不了价值判断——量刑的伦理权衡必须人来。
- 人类专家强在因果与责任，弱在覆盖与更新速度。
- 可信路径：数据发现草稿，专家审核定稿——和记忆更新"提案与审核分离"是同一条原则。

**9. 请为一个 Markdown 用户记忆库同时设计增量更新与定期整理流程。如果 Reviewer 与 Proposer 使用同一模型，且只能看到 Proposer 挑选的对话片段，系统仍可能合入哪些错误？请从模型独立性、证据覆盖和工具权限三方面说明你的改进。**

Answer:
书里给了成套方案——把知识库当代码库，每次变更是一个 PR。
- 增量更新四步：Proposer 在工作分支提最小 diff，先检索已有知识再增删改并维护链接和元数据；Reviewer 拿变更前知识、diff 和原始证据独立核验每个断言；双方迭代至收敛，设最大迭代次数，超限转人工而非默认放行；合入后 CI 查格式链接元数据，再从已合入版本重建索引。
- 定期整理：回到原始数据去重去旧合并，不能只在摘要间改写——早期遗漏和误读会代代相传；冲突不取舍而是场景限定，各自适用条件写进知识；整理产物同样走分支加异源审核，拆成多个 PR 但共享覆盖清单，全部通过后回放典型检索用例确认旧知识没变得不可见。
- 三层分离：原始证据层只增不改、知识层持续修订、服务层索引是可重建的派生物——每条线上知识都能回答从哪条证据来、谁在什么时候批准。

同模型同视野的失败模式：
- 确认偏差：自己提案自己审，天然倾向放行——同一模型的盲点在两个角色里原样复现。
- 证据截断：Proposer 只给有利片段，Reviewer 看不到反证，被截断的矛盾信息合入后就是定时炸弹。
- 幻觉来源：无核验手段时 Reviewer 只能信提案文本，编造的"用户说过"直接入库。

三方面改进，书里都有对应：
- 模型独立性：异源互审——两个 Agent 优先用能力相近但不同家族的模型，如 Proposer 用 Claude、Reviewer 用 GPT；不同训练数据降低同处犯同类错误的概率，能力不宜悬殊否则审不动复杂证据。
- 证据覆盖：两个 Agent 都必须能按需查询完整知识库和原始证据库，而不是只收上游挑好的片段——Reviewer 主要核对证据和 diff，不是沿着 Proposer 的结论复述一遍。
- 工具权限：二者都必须是有工具的 Agent 而非两次 API 调用——Proposer 能检索已有记忆，Reviewer 能追证据、比版本、跑检查；权限强制分工——Proposer 只写工作分支，Reviewer 只读证据，只有合并流程可以更新主分支和线上索引。
