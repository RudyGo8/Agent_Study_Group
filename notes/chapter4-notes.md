# 第四章学习笔记：工具

## 1. 总结

- **五类工具两个特征**：调用方向——谁发起；作用对象——作用于什么。感知获取信息、执行改变世界、协作驱动其他 Agent 或人、用户沟通向用户传递、事件触发由 Agent 注册外部事件唤醒。前三类 Agent 主动调用，本章展开；事件触发与用户沟通依赖事件驱动运行时，留第六章
- **能力表达两形态**：专用代码工具确定性高、可测试，但每个占数百 token、数量膨胀毁 KV Cache；Skill + 通用执行器用自然语言文档描述流程，少量通用工具覆盖大量场景。三维决策：参数复杂度高选专用、变更频繁选 Skill、强模型可多用 Skill 弱模型需要 schema 引导
- **粒度与通用性**：功能相似加使用场景重叠才整合——read_document 用 file_type 参数吃掉三种文档提取；超过 100 个工具模型就容易选错。通用工具优于专用，除非有安全、权限、性能理由——code_interpreter 是元能力，一个沙盒解释器顶数十个专用计算器，还能处理没想到的边缘场景
- **描述的艺术**：写"什么时候用"而不只"能做什么"；边界比能力更重要——大多数调用失败的根因是模型不知道工具不能做什么；参数用具体例子代替抽象规范；附 1-5 个真实调用示例，准确率可从约 72% 提到 90%。调试铁律：频繁选错工具先改描述，别急着换模型
- **参数保真性**：静默输入转换——Cursor 弯引号案例，模型看到的世界和工具操作的世界不一致，制造无法自诊的系统性故障；静默参数注入同理。原则：两个世界之间不能有系统性偏差，必须规范化就在描述里说明并在返回中告知
- **工具设计三代演进**：API 封装 → ACI 原则——工具对应 Agent 的目标而非底层 API，对标 HCI → 第三代优化调用、发现、串联：示例驱动调用、动态工具发现、代码编排执行——中间变量留在执行环境只回传结果，token 可降约两个数量级
- **MCP 统一插座**：Anthropic 2024 底开放标准，工具、资源、提示三类原语分别对应可执行操作、可读数据、可选用模板；一次开发处处可用。局限：管能力调用标准化，不管事件运行时。5 个服务器可引入约 55K token 工具定义——Cursor 描述同步进文件夹按需查省 46.9%；Pi 干脆不内置 MCP，用带 README 的 CLI + Skills
- **MCP 与 Skills 分工**：MCP 管互操作，Skills 管选择过载——把"工具选择"问题转化为"知识检索"问题，后者正是 LLM 擅长的；两者不互斥，Skills 也可经由 MCP 传递
- **MCP 安全四风险**：工具描述投毒——description 原样进上下文，是提示注入的变种；恶意或被劫持服务器——供应链；同名工具遮蔽——诱导把调用和敏感参数路由给攻击者；凭证管理。缓解：描述当不可信输入审计、锁定版本拒绝静默更新、最小权限凭证
- **感知工具**：核心是控制输出量防上下文爆炸——超阈值集成上下文感知压缩；搜索返回结构化候选加分页让 Agent 决定翻不翻；读取支持 offset/limit、截断必须显式可见——静默截断让 Agent 误以为看到了全部；只读红利：可缓存、可并行
- **多模态三路线**：原生多模态上限最高——直接看到布局图表；提取为文本最省 token——PDF 一页截图上千 token、文字只几百，但丢版式丢图表；工具化分析折中——analyze_image 接文件加问题返回分析，上下文只留问答，主模型不必多模态
- **执行工具安全多层**：输入验证快速失败——发现异常立即拒绝不做智能修正；权限控制——黑名单只是基础层可被变形绕过；提议者-审核者——事前审批用不同家族相似能力模型互审，认知多样性，拒绝理由作为工具结果进轨迹；事后验证靠模态切换——渲染成图再看、沙盒里真跑
- **Sidecar 机制**：轻量模型与主流式输出并行，门控单次工具调用；只读结构化字段——防藏在上下文里的话术操纵；轻量模型够用因为审的是分类问题不是开放式思考；配拒绝熔断器——连续拒绝即回退人工，不让 Agent 死循环
- **执行工具其余要点**：可验证就自动验证——写完文件立即跑 linter 返回结构化错误；长输出头 50 尾 50 加中间提示加文件引导；venv 不是沙盒——只隔离包依赖不隔离文件系统网络，隔离强度进程级、容器、microVM 递增；幂等性——唯一标识去重或先查询后变更，不可幂等的邮件转账用预检-确认两段式
- **协作工具**：专业化分工优于全能 Agent；子 Agent 提示词四要素——角色清晰、上下文来源标注防注入、任务边界、输出格式标准化；三组原语——启动取消、消息传递、发现；之上承载四种形态——同步、异步、流式、多轮交互；HITL 要超时降级加反馈循环——人的批准拒绝理由沉淀为知识库或训练数据
- **主动工具发现**：从被动接受到主动声明——Agent 意识到能力缺口时用自然语言声明，系统语义匹配注入；MCP-Zero 在 2800 工具上省 98% token；两层路由先服务器级后工具级；匹配不到就明确返回未找到。动态加载的缓存解法：新 schema 追加到上下文末尾、固定在轨迹原位置——工具定义必须放最前面不再是铁律
- **Skills 作为工具发现**：目录数百 token 常驻，需要时顺索引查阅像查工具书；不需要嵌入索引基础设施。模型原生工具对模型友好——JSON schema 加限制采样强制格式；Skill 对人类编写者友好——自然语言、错误局部化不牵一发动全身。但 Skill 对模型要求更高——引号转义规则复杂且跨平台不一，参数结构复杂时仍建议用原生工具，或让 Agent 把结构化参数写成 JSON 文件再在命令行导入。Skill 的 KV Cache 升级：预编译一次，RoPE 重定位以 O(L) 代价粘贴到任意位置——skill 从一段文本变成可复用的缓存对象
- 小结钩子：本章讲 Agent 如何使用工具，下一章回答 Agent 能不能写代码创造工具

## 2. 实验

**4.1 感知工具 MCP 服务器**
论证 五类感知场景打包成一个 MCP 服务器——搜索、多模态理解、文件系统、公开数据源、私有数据源；MCP 三类原语的完整实践；其中大部分功能第 5 章将论证可用七个核心工具加 Skill 覆盖

**4.2 多模态信息提取：三种范式对比**
论证 三条路线各擅其场——原生多模态分析图表布局最佳；提取为文本在纯文本文档上成本效益最高但完全无法处理视觉查询；工具化模式交互灵活，低成本初步分析加按需深度，但一次性端到端深度理解不如原生

**4.3 执行工具 MCP 服务器**
论证 安全体系完整落地——写入后自动 linter 返回结构化错误、危险命令检测、沙盒代码解释器加审批、长输出截断持久化；执行-验证-反馈闭环的工程实现

**4.4 协作工具 MCP 服务器**
论证 子 Agent 生命周期原语——spawn、send、cancel、status 支持同步异步；人类协作——审批请求超时降级、多渠道通知；对比最小化传递与 LLM 生成上下文两种交接方式

**4.5 主动工具发现（三星）**
论证 小模型加大工具集的救赎——Qwen3-4B 面对 120+ 工具全量注入超 50K token，指令遵循严重退化，错选 Web Search 而非 Yahoo Finance；实验组只留 web_search、code_interpreter 加 discover_tools 元工具，自然语言声明缺口返回 3-5 个候选，schema 追加到历史；主动发现不仅救大模型的千工具场景，更让小模型在上百工具下保持可用

## 3. 思考题

**1. MCP 标准将工具定义从 Agent 框架中解耦了出来。但标准化也意味着复杂的工具交互模式（如流式输出、双向通信、有状态会话）可能难以在标准协议中表达。你认为 MCP 未来最需要扩展的能力是什么？**

Answer:
最缺的是事件与长任务运行时的标准化。
- 现状缺口：协议已支持多轮交互、变化订阅、长任务，但解决的是"一次工作流如何继续"，不管"Agent 始终在线"——新邮件唤醒、外部回调恢复任务，目前都要在协议之上另行构建。把注册、订阅、唤醒的语义标准化，是最大的扩展空间。
- 其次：流式渐进结果的标准表达——长任务的中间产出如何规范地流回；有状态会话的断点恢复——中断后凭状态续跑而不是从头再来。
- 一条约束：扩展应守住分层——MCP 管能力调用标准化，事件接入、调度、并发、唤醒归框架层。若插座标准吞下发电厂，标准变重，生态反而做不大。

**2. 在 MCP 生态中，不同的 MCP 服务器可能提供功能高度重叠的工具。当 Agent 面对多个来源不同但功能相似的工具时，应该如何选择？如果不同来源的同名工具在行为上略有差异（比如一个返回摘要，另一个返回全文），Agent 是否有能力感知并利用这种差异？**

Answer:
选择策略：
- 信任优先：有官方或已审计来源时优先——同名工具遮蔽正是攻击手段，选择必须带服务器身份感知，不能只看工具名。
- 描述对比：看边界和代价标注——描述应该主动声明与相邻工具的差异点，重叠工具的取舍信息要在接入层写清楚。
- 治理收敛：接入审查时合并或标注主备，别把选择负担全推给模型——这是框架层的活。

能否感知差异：
- 有条件地能。差异写进描述，选择时就能用；没写，只能靠调用后观察发现，代价是一次试错。
- 让差异在使用中显式化：返回值自描述——本结果为摘要，全文请用另一工具——模型下一轮就能利用这个信息修正选择。

**3. 本章提出了"执行-验证-反馈"闭环（如写代码后自动运行 linter）。这种"操作后立即自动验证"的模式还可以应用到哪些工具场景？是否存在某些操作，其验证本身的成本或风险超过了操作本身，导致这种模式不可行？**

Answer:
可推广场景：
- 配置修改后在沙盒试运行验证生效——书里事后验证的原例。
- 发邮件前渲染预览检查排版、SQL 变更前 EXPLAIN 看影响行数、翻译后回译比对、部署后健康检查、删除前先 dry-run 列出将删的文件。

不可行的场景：
- 验证本身有副作用：验证"通知发出去没有"的办法就是再发一次。
- 验证成本远超操作：为一次几分钱的 API 调用跑一次昂贵的模型审查，得不偿失。
- 验证引入新风险：在生产库上"试运行"写操作，验证动作本身就是事故。
- 时效优先：交易、熔断这类等不起验证的操作。

判断式：验证的价值 = 错误代价 × 发生概率，拿它对比验证的即时成本与风险。不可行时降级——改成操作前预检，或事后抽样。

**4. 本章提出了"工具爆炸"问题——Agent 面对数千个工具时选择精度下降。除了主动工具发现，还有哪些方案？可以参考人类专家在面对大量可用工具时的策略。**

Answer:
人类专家的策略映射：
- 专家不背工具目录，先分类再找：这是哪类问题、用哪箱工具——对应层次化组织，搜索、读取、解析、查询分组让模型先定位组再选工具。
- 专家有惯用工具集：常用的就那几件，长尾的查了再说——对应核心工具常驻加长尾按需，Pi 的哲学正是如此。
- 专家问同行、查手册——对应 list_agents 发现协作者和 Skills 按需查阅，顺索引翻到哪条读哪条。

其他方案：
- 源头减量：Skill 加通用执行器替代专用工具——第 5 章的七个核心工具路线，工具数从根上砍下来。
- 代码编排执行：一段代码串起多个基础工具，组合爆炸变成代码问题——中间变量不进上下文，还省 token。
- 组织治理：接入审核砍掉重叠工具——工具爆炸一半是管理问题不是技术问题。
- 根本出路是书里那句：把工具选择问题转化为知识检索问题——检索正是 LLM 的长项。
