# 第二章学习笔记：上下文工程

## 1. 总结

- **上下文决定能力上限**：中等模型 + 精心组织的上下文，往往胜过顶级模型在信息匮乏下的瞎摸索。Agent 是"永远的新员工"，给足背景才能干活；上下文工程不只是技术问题，还是组织问题——对远程协作友好的团队天然对 AI 友好
- **上下文结构 = 静态前缀 + 动态轨迹**：系统提示词 + 工具定义是前缀，用户消息 + 模型回复 + 工具结果是轨迹；API 无状态，每轮都由 Harness 重新构造完整 c_t
- **KV Cache 三条铁律**：系统提示词和工具定义定了就别改；动态信息永远追加到末尾，不改前缀；用标准 API 消息格式，不自行拼接文本。改前缀一个字，其后缓存全作废——时间戳故事：一行 Current time 让首 token 延迟从 0.5 秒涨到 3-5 秒、月账单几乎翻倍
- **两级缓存**：KV Cache 是推理引擎层的中间计算复用，Prompt Cache 是其上的跨请求缓存，都只认 token 前缀字节序列
- **提示工程**：流程驱动优于规则堆砌——按执行顺序组织规则；Few-shot 在期望输出难以用规则描述时给两三个高质量示例，效果常胜过等量篇幅的抽象规则，且示例一旦确定要保持字节级稳定（动态挑示例 = 每次改前缀 = 缓存持续失效）；工具描述是给模型看的文档；提示注入是上下文安全的核心威胁
- **Skills 渐进式披露**："怎么做某类事"抽成独立单元，目录常驻上下文、正文按需加载——用几十 token 的元数据撬动几千 token 的领域知识
- **状态栏**：把隐式状态显式化——进度、计数、token 余量写进上下文，模型从"数数归纳"变成"直接读取"；小模型配状态栏，准确率可接近前沿大模型
- **压缩与隔离**：上下文学习本质是检索而非推理——堆信息不如组织信息；压缩必须任务感知，保留决策、约束、失败、来源四要素；**隔离优于压缩**——子 Agent 开新上下文只带回结论，增长从二次方变线性
- 本章管一次任务之内的状态，第 3 章扩展到跨任务的用户记忆和共享知识库

## 2. 实验

**2.1 本地 LLM 服务部署**：论证 0.6B 小模型 + 合理提示词也能可靠完成工具调用，模型大小不是唯一决定因素；顺带实测 KV Cache——改系统提示词一个字，首 token 延迟显著上升

**2.2 注意力机制可视化**：论证 注意力就是"找重点"——Query 与 Key 点积算匹配度、对 Value 加权；这是理解 KV Cache 为何有效、为何前缀要求苛刻的基础

**2.3 常见错误上下文模式**：论证 **五种**有害模式——动态系统提示词、动态用户配置、工具动态排序这三种毁缓存（且实验表明固定排序对模型选工具几乎无影响），滑动窗口丢关键工具结果导致重复调用，文本格式化偏离训练格式致解析混乱。解法全部收敛回三条铁律

**2.4 提示工程消融实验**：论证 基于 Tau-Bench 客服场景，信息组织的混乱使成功率下降 30% 以上——提示词的"组织方式"本身是性能变量

**2.5 提示注入攻防**：论证 注入攻击的原理与防御可构造、可评估——不可信内容必须隔离

**2.6 Skills 生成演示文稿**：论证 渐进式披露——Agent 从元数据目录看到 Skill 描述、按需加载正文，即可完成论文转 PPT 这类复杂任务

**2.7 去 AI 味写作 Skill**：论证 三五篇范文可沉淀为可加载、可检查的写作 Skill，在新题目上复现作者偏好

**2.8 状态栏注意力验证**：论证 对照实验——无状态栏时注意力分散、思考 token 在数数统计；有状态栏时注意力直接命中状态区。量化结论：思考 token、延迟、花费各降约一个数量级；无状态栏时思考量随上下文持续增长，有状态栏后基本恒定

**2.9 状态栏技术集**：论证 **时间戳跟踪、工具调用计数器、TODO 列表管理、详细错误信息、系统状态感知**五种技术；关键细节——时间戳放消息前缀而不是系统提示词，否则毁缓存。实验数据：TODO 启用后平均 15 次迭代完成任务，禁用要 21 次且漏子任务；详细错误信息使错误场景成功率从 60% 提到 95%

**2.10 压缩策略对比（三星）**：论证 压缩必须任务感知——无压缩 5 轮爆 128K 窗口任务失败；非任务感知摘要碎片化，个体摘要 12 次迭代 27.6 万 token；上下文感知压缩 7 次迭代 4 万 token、压缩率 3.0% 仍保留关键信息；带引用版语义有损但源链接无损可回溯；自适应窗口化 80% 阈值才触发、批量压缩、[COMPRESSED] 标记防重复

## 3. 思考题

**1. 实验 2-3 发现，滑动窗口对话历史会导致 Agent 反复执行相同的工具调用。但完整保留历史又会让上下文不断膨胀。设计一种策略，既能避免信息丢失，又能控制上下文长度，且不破坏 KV Cache 前缀。**

Answer:
分层处理，各层管各的事。
- 前缀层永远不动：系统提示词加工具定义一旦确定不改，动态信息一律追加到末尾。
- 近期原文保留：最近 K 轮完整保留且只追加——只追加的历史天然缓存友好。
- 远期摘要归档：更早的轮次合并成摘要，在段落边界替换，一次压缩只废一次缓存，摊销后可接受。
- 原文外置：被压缩的原文落盘或进外部存储，上下文留指针——需要时工具取回，信息不丢。
- 状态栏兜底：一份紧凑的当前状态常驻上下文，关键结论永远可见。
- 何时压有标准答案——实验 2-10 策略六自适应窗口化：80% 阈值才触发，触发时批量压缩，[COMPRESSED] 标记防止重复处理；任务初期上下文充足时不急着压，最大限度保留原始信息。

**2. Qwen3 的 Chat Template 思维链保留机制只保留"最后一个真实用户消息之后"的思考。如果一个 ReAct 循环跨越了上百轮工具调用，累积的思考内容可能消耗大量上下文。你会如何修改这个机制来应对超长循环？DeepSeek R1 曾要求剥离全部历史思考，而 DeepSeek V4 反转为强制回传全部 reasoning_content——对比这两种相反的策略，各有什么利弊？这个反转说明了什么？**

Answer:
折中——按预算保留最近的思考，更早的压成一句决策摘要；或把思考外化到文件，上下文只留指针。
- R1 剥离的利：省 token，防止旧思路污染后续推理；弊：丢失决策依据，长任务前后矛盾——正是实验 1-1 no_reasoning 臂的样子。
- V4 全回传的利：决策连贯，append-only 对缓存友好；弊：token 贵，长链累赘。
- 反转说明：没有永远正确的手段，只有随模型能力变化的权衡——模型思考质量和抗干扰能力上来了，回传就从负担变资产。呼应第 1 章思考题 10：手段会过期，原则不会。

**3. 上下文感知压缩实验中，从约 148K 个字符压缩到约 2,000 个字符，这种极端的压缩是否存在"不可逆信息损失"的风险？如何解决？**

Answer:
存在——压缩天然有损，丢的恰恰可能是后面要用的。
- 结构化保四要素：决策、约束、失败教训、来源，其余细节可丢。
- 原文外置加指针：原文落盘，摘要进上下文，需要时工具取回——损失可逆化。
- 书里给出了成品方案——实验 2-10 策略五带引用的上下文感知：内容经语义压缩是有损的，但每条事实附带来源 URL 这个无损索引，理论上可随时回溯到原始信息。有损压缩 + 无损索引是标准解法。
- 关键数值不进摘要：精确数字、引用链接走外部存储，摘要只留定性结论。

**4. Agent 状态栏将隐式状态显式化。但如果状态栏本身包含了错误信息（比如工具计数器出了 bug），Agent 可能基于错误的信息做出有害的决策。这种"元信息可靠性"问题如何缓解？**

Answer:
书里的直接证据比想象更严重——模型几乎无条件地相信状态栏：你写"打了 3 次电话"，它就当真是 3 次，不会自己重算。所以：
- 状态栏尽量用代码维护，绝不让 LLM 一次性批量统计——LLM 数数本来就容易错，逐条抽取、代码汇总。
- 状态栏是对原始上下文的有损投影——只提前算了"预想会被问到"的维度。删原始记录省 token 可以，但只要有一个问题落到没算过的维度上，准确率断崖式崩塌，所以不要无脑删原文。
- 交叉校验：状态栏计数与轨迹实际条数定期对账，不一致即告警降级。
- 状态栏是优化不是依赖：它失效时系统应能退回完整轨迹模式，只是慢。

**5. 提示工程消融实验表明，信息组织的混乱导致成功率下降 30% 以上。但在实际开发中，系统提示词往往由多人在不同时间维护。你会用什么工程实践来防止系统提示词的"熵增"？**

Answer:
把提示词当代码管理。
- 版本控制加评审：提示词进 git，改动走 PR，谁改的、为什么改、依据什么证据可追溯。
- 回归测试兜底：用消融实验做基准，改完跑一遍成功率，掉了就拒合并。
- 结构化分区加标注：每条规则标注来源和存在理由，定期清理无证据的死规则。
- 一致性检查：工具化检测规则冲突和重复。

**6. 本章提出"上下文学习本质上是检索而非推理"。如果这个论断成立，当前所有基于"把更多信息塞进上下文"的优化方向都需要重新审视。你认为应该如何突破这一局限？**

Answer:
承认检索本质，把优化从"塞更多"转向"取更准"。
- 被动堆放改主动检索：RAG 按需取回，相关性排序进上下文，而不是整块塞入。
- 渐进披露：Skills 目录常驻、正文按需加载，索引层永远小于正文层。
- 推理外化：计算交给代码解释器，上下文只放结论——不在上下文里"推演"，只用上下文"取材"。
- 为检索而组织：结构化分区、位置固定、标记清晰，让"检索"更容易命中。

**7. Skills 的渐进式披露只在 Agent 判断需要时才加载完整内容。但这个判断本身依赖模型的能力——如果模型不知道自己不知道什么，就无法正确触发 Skill 的加载。这个"元认知"问题如何解决？**

Answer:
把元认知从模型自测外化为系统供给。
- 目录即答案：SKILL.md 的 name 和 description 写清触发条件，常驻上下文——"知道自己不知道"变成"看得到目录"。
- 触发工具化：由路由或检索层判断该加载哪个 Skill，不依赖模型自省。
- 卡住即扫描：检测到任务停滞时，系统主动扫描 Skill 目录并建议加载——用失败信号补元认知。
- 实验 1-1 的教训通用：别赌模型的状态感知，把状态摆到它眼前。

**8. Skills 机制中，Agent 从 SKILL 文件中动态读取提示词之后，后续的操作能否正确遵从这些指令？不同的模型对 Skills 模式的支持有什么区别？**

Answer:
不总是——指令遵循随上下文增长而衰减，中间内容易被淹没。
- 强指令遵循模型较好，小模型容易"读了不用"，skill 加载了但行为没变。
- 缓解手段：Skill 指令放上下文末尾利用近因效应；执行中在状态栏回显当前 Skill 和关键约束；完成一步校验一步。
- 验收上可以用轨迹检查：Skill 加载后的操作是否真的引用了其内容——这是可观察的证据。

**9. 本章强调动态信息（如系统时间戳、工具列表顺序）的变化会破坏 KV Cache 前缀命中。在一个拥有大量工具且工具集频繁变动的生产系统中，你会如何设计上下文布局来最大化缓存命中率？**

Answer:
按变动频率分层，越稳的越靠前。
- 三层布局：系统提示词最前，稳定工具池其次，动态内容一律尾部追加。
- 工具分池：高频核心工具固定顺序进前缀；长尾工具按需注入上下文末尾，变动只废尾部。
- 时间类信息降频：时间戳不放系统提示词，放用户消息前缀或需要时工具获取。
- 顺序确定性：动态工具列表按固定键排序，同样的集合永远产生同样的序列——缓存只认字节。
