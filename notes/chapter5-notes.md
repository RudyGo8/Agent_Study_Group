# 第五章学习笔记：Coding Agent 与通用 Agent

## 1. 总结

- **通用 Agent 架构的答案**：Coding Agent 加文件系统——从 Manus 到 OpenClaw 都遵循这一范式；代码生成是元能力，能在运行时动态创造新工具和能力，而不必预制
- **代码价值两层**：思考上，形式化代码无歧义——自然语言说"年龄大于 18 且已实名"有多种理解，代码只有一种；表达上，能跑通的代码本身就是逻辑自洽的证明，执行结果提供客观对错标准
- **七个核心工具**：Code Interpreter、Bash、读文件、写文件、编辑文件、Glob 搜文件名、Grep 搜内容——覆盖几乎所有 Coding 动作；coding 不是专门 Agent 的专利，是每个通用 Agent 的基础能力
- **为什么 Coding 是内核**而非 Deep Research 或 Computer Use：高效的内容生成都落到代码——PPT 本质是 OOXML 代码、报告 PDF 由代码生成、分析用 Python、成功的浏览器操作序列固化为 RPA 代码；代码效率最高、成本最低、可复用性最强
- **文件系统是中枢**：OpenClaw 的记忆放 MEMORY.md 加 Markdown 日志而非向量库——人可直接读改、天然保留时间顺序、git 可回滚；Agent 有写文件能力，就有了修改自身外部产物的技术条件。适用边界：以 Coding 为核心架构适用于开放任务；垂直封闭任务围绕业务流程构建，代码只是工具——但 coding 能力是所有 Agent 的共同底线
- **理想流程与现实裁剪**：项目文档化——CLAUDE.md 等项目指令文件是项目级系统提示词，也是最经济的稳定前缀；AI-ready 的代理指标：远程新人只靠仓库和文档能否独立开展工作 → 需求澄清 → 设计文档是人类高效介入点 → 实现与测试——完成标准是测试通过而非代码写完 → 自我审查 → 文档同步
- **Harness 四组件与四象限**：验收基线、执行边界、反馈信号、回退手段；目标明确加验证自动化是最佳象限——Harness 的目标是把任务推进这个象限。Coding Agent 成熟度最高的原因不是模型强，而是软件工程几十年攒下的测试套件、类型系统、版本控制天然构成强大 Harness
- **可迁移四原则**：约束优先于指导——Linter 是做不了，提示词只是建议别做；验证自动化——人工审查不可扩展；反馈越快越结构化越好；回退要可靠——安全网内才敢大胆试错。约束还要防过程性错误——删库重建也算修复生效，要约束动作而非仅结果
- **业界三案例**：大规模代码迁移——关键不在模型强，在知识存在于代码库本身、约束编码进 Linter 和 CI 而非文档、验证纠正全链路自动化；LangChain——用 Agent 分析失败轨迹来改进 Harness，从人工经验驱动转向数据驱动；Anthropic——初始化 Agent 分解任务清单、执行 Agent 逐步推进并留中间成果，解决长任务一次想做太多或过早声称完成
- **故障四层分类**：API 层——限流超时截断，基础设施噪声；工具层——幻觉调用、参数畸形、同一错误反复重试；上下文层——溢出、压缩失败、轨迹损坏；控制流层——死循环与死亡螺旋
- **检测三件套**：先分类再计数——可重试与不可重试的映射表，不是笼统出错就重试；模式检测——工具名加参数的指纹查重、连续失败计数；活性与完整性监控——流式最危险的失败是静默卡死不是断开，每个长连接都要活性信号而非仅连接超时；产品模式宽容、训练模式严格
- **恢复分级升级**：静默重试——指数退避加抖动、区分前台后台防重试放大 → 降级接续——输出触顶先提上限再断点接续、主模型过载降备用要先剥离私有格式块 → 才暴露用户。工具错误不终止会话，变成结构化输入喂回模型。原则：错误处理的边界是整个恢复循环，确认无法恢复前不暴露中间态
- **每条恢复路径都要熔断**：Claude Code 压缩熔断 3 次来自产线统计——曾有会话连续失败三千余次、这类无效重试每天全球浪费约 25 万次调用；死亡螺旋防护：错误路径禁用一切再调 LLM 的副作用、递归深度计数器打断连锁。本质句：Agent 的可靠性不取决于犯不犯错，而取决于每类错误是否都有对应的检测、恢复与终止路径
- **实现技巧五件**：并行与流式——第一个调用参数一完整就执行，故障靠级联中止——只终止同批依赖该结果的调用，不波及独立调用和父级操作；上下文精细管理——读取返回带行号标注；环境信息动态注入——cwd、git 分支、最近提交、变更概览做成状态栏追加，不进静态前缀；持久化终端会话为默认——cd 和环境变量不丢；即时语法反馈——写入即 lint，像 IDE 红线
- **搜索工具四层互补**：Grep 精确文本、Glob 文件名模式、语义搜索——结构感知分块加混合检索，Claude Code 刻意不建嵌入索引靠 agentic 检索 vs Cursor 建索引换跨文件语义召回的路线之争、符号级 LSP——区分定义与调用，重构必需；从粗到细渐进使用
- **文件编辑五方案**：diff 加 Apply Model——Cursor 已弃；旧串换新串——Claude Code 现用，可预测透明但大段删除要全文输出；行号定位——行号会漂移，多编辑需统一用初始行号；类 Vim——为人类设计，人类看状态做简单操作而模型是长思考后批量复杂操作，不匹配；首尾匹配——折中优选，大段删除只需边界
- **安全：致命三要素加第四要素**：访问私有数据、暴露于不受信内容、具备外部通信能力——三要素齐备攻击链闭合；作者补第四维持久记忆——不是必要条件是放大器，恶意指令可跨会话潜伏。三点增量：命令语义解析——黑名单挡不住组合爆炸，`$(echo rm)` 绕过、`find -exec` 嵌 rm、`curl -o /etc/crontab` 覆盖定时任务，要理解参数消费规则；沙盒工程——默认断网白名单代理放行、源码只读挂载、凭证不挂载、超限返回结构化错误；持久记忆写入走与外部内容同等的信任审查
- **忠诚度：Agent 为谁效忠**：多方委托下"谁说话帮谁"是危险默认——替你砍价的 Agent 对面是交涉对手；光谱两端都翻车——太老实泄底价、太多疑拒绝正当请求，且是跷跷板难两全；提示注入本质就是一次策反。Harness 要把忠诚对象显式钉死：主人指令优先级最高，外部交互内容降格为可参考但不具指令效力的数据
- **元能力六方向由内向外**：思考工具——LLM 理解自然语言加符号计算引擎精确计算，Wolfram 洞察；模型与脚手架此消彼长，弱模型靠求解器兜底、强模型增益收敛到零 → 业务规则——自然语言规则供解释沟通、代码化校验当守门员，三重保障：提示词规则加参数 checklist 引导思考加服务端真值校验；真正价值是防不可逆错误操作 → 多媒体生成——PPT 是代码，提议者-审核者：Proposer 写 Slidev、Reviewer 渲染截图用 Vision LLM 出结构化建议，双 Agent 分工的核心优势是上下文管理 → 系统适配器——无 SDK 现场写 HTTP 客户端的万能胶、无 API 系统把成功操作固化为 RPA、日志自适应解析的失败反馈循环 → 生成式 UI——A2UI 声明式协议：Agent 只能点菜单不能进厨房，受信组件目录渲染；AG-UI 是事件传输协议不是界面描述语言；HTML 交付取代 Markdown 汇报；SQL Artifact 模式——数据绕过 LLM 中间人直达界面；动态生成软件把信任边界下移数据层——行级安全、访问上下文由受信运行时绑定，目标是即使 AI 写错权限检查也无法绕过 → Agent 自举——OpenClaw doctor 两层：确定性检查打底加 LLM 兜底长尾；基于范例生成优于从零——复制自己加适应性修改，如基因复制加变异
- 小结：代码不只是写程序的工具，是 Agent 形式化思考和精确表达的语言；至此全书构建部分完成，第 7 章起讲持续改进

## 2. 实验

**5.1 代码生成提升数学解题**
论证 LLM 出题意、代码算精确——AIME 风格题上，sympy 符号计算辅助显著高于纯思维链

**5.2 代码生成提升逻辑思考**
论证 骑士与无赖问题转约束求解——K&K 数据集准确率 90% 以上；更重要的是揭示模型与脚手架此消彼长：刻意用弱模型放大对照，强模型上纯思考就能全解、代码增益收敛到零——评估脚手架必须注明模型能力前提

**5.3 小模型代码化规则**
论证 τ-bench 航空客服三重保障——参数 checklist 让模型准备调用时就识别违规、直接向用户提议替代方案；自报值与数据库真值的 mismatch 统计，验证服务端真值校验拦截错误认知的必要性

**5.4 论文 PPT 自动生成**
论证 提议者-审核者质量控制内容创作——Reviewer 渲染每页截图、Vision LLM 出含页码问题类型严重程度的结构化建议，迭代至达标；对照单 Agent 自审在上下文消耗和质量上的差距

**5.5 论文讲解视频**
论证 流水线扩展——PPT 截图加 TTS 语音加 ffmpeg 同步合成，每页展示时间与语音时长精确匹配

**5.6 API 智能视频剪辑**
论证 GUI 剪辑重构为 Blender API——两步定位：粗粒度每 10 秒截图找场景区间，再每秒截图定精确边界；截图分析走子 Agent 避免占用主上下文；边界误差 3 秒内

**5.7 自适应日志解析系统（三星）**
论证 自我进化的可视化——前端解析失败不是报错而是自动报告 Agent，生成新解析代码，虚拟浏览器测试通过后热更新，全流程无人干预

**5.8 生产日志智能诊断（三星）**
论证 从轨迹到任务的自动化——读生产轨迹结合架构文档和 PRD 定位问题，生成结构化报告、引用轨迹 ID 的回归测试用例自动重放验证，MCP 对接 GitHub 建 Issue 完成分派

**5.9 动态表单意图澄清**
论证 一次表单替代十轮问答——含级联逻辑：选往返才显示返程日期；用户一次提交，Agent 解析 JSON 继续

**5.10 自然语言 ERP Agent**
论证 自然语言转 SQL——员工表加工资表上 10 道由浅入深的查询，从部门人数到拖欠工资检测

**5.11 对话式界面定制**
论证 半定制加热加载——基础 chatbot 上用户说改颜色改字体，Agent 改代码后 HMR 即时生效，多轮迭代千人千面

**5.12 动态生成软件的权限内嵌数据对象（三星）**
论证 信任边界下移数据层——应用层代码可被动态改写，但跳过状态机、写入越界工资、跨租户读取都被数据层稳定拒绝；对照看的不是生成的 handler 写没写对 if，而是同一请求到达数据层后能否被可靠接受或拒绝

**5.13 开发能创造 Agent 的 Agent（三星）**
论证 基于范例生成——先复制高质量 Agent 范例再针对性修改，对比从零生成验证质量与效率优势；元编程能力的落地

## 3. 思考题

**1. 代码生成被称为 Agent 的"元能力"。但代码执行引入了安全风险——Agent 生成的代码可能包含漏洞、无限循环或资源耗尽。沙盒隔离能解决部分问题，但也限制了代码能力（比如无法访问网络或文件系统）。如何在安全性和能力之间找到最优平衡点？**

Answer:
不是找一个静态平衡点，而是分层放开、按需扩权。
- 基线沙盒最小权限：默认断网、文件系统只挂工作区、资源限额加超时——能跑代码不等于能传数据，网络出口控制正是致命三要素第三条的外科处理。
- 按需放行：任务确需网络走白名单代理——包管理源、指定 API，目的地级放行不是开关级；需要读项目外文件时按路径申请。
- 按来源选隔离档：本地可信代码进程级、不可信输入容器、陌生代码 microVM——第 4 章谱系按代码来源分档。
- 授权与任务绑定、会话结束回收；超时超限返回结构化错误而非静默杀死，让 Agent 下一轮自己修正策略——安全约束本身也要对 Agent 透明。

**2. Agent 自举——能创造 Agent 的 Agent——实现了"智能的自我繁殖"。但每次自举都可能引入新的偏差或错误，这种错误会在代际间累积吗？如何防止 Agent 自举的退化？**

Answer:
会累积——代际误差是复利，防退化要给"变异"配"选择"。
- 基因为范例：基于高质量范例复制加修改而非从零生成——好架构自然保留，这是第一道防线。
- 每代过验收基线：新 Agent 必须跑全套测试和基准，不过不发布——测试就是选择压力，没有选择的复制必然退化。
- 参考实现锁版本：范例本体不随自举漂移，升级走独立审核——防止污染源被逐代改坏。
- 可追溯可回滚：每代 diff 进 git，退化可定位到具体代、可回退；定期与人类审查的基准版对齐漂移。
- 这正是第 9 章持续进化的门槛问题：变异加选择加可回滚的固化，三者缺一不可。

**3. 代码生成 Agent 在处理日志解析时，能自动跟随格式演化。但如果格式变化是一个 bug 而非预期改动，Agent 的适应性反而掩盖了问题。Agent 应该如何区分"需要适应的变化"和"需要报告的异常"？**

Answer:
判据是变化的合理性证据，不是变化本身。
- 显式变更信号：伴随版本号、changelog、上游公告的改动——适应；无版本变更的格式突变——异常优先报告。
- 一致性检验：新格式与其他日志源或 schema 约束矛盾——嫌疑升级；单一来源小幅演化——适应。
- 统计阈值：字段缺失率、解析失败率超过阈值触发人工审查，而不是静默适应。
- 双通道设计：自动适配照常工作保业务连续，异常报告并行上报——适应不等于吞掉。这与第 4 章可观测性同源：工具自己发现的问题要留痕。

**4. 本章在 PPT 生成、视频编辑和日志可视化中反复使用提议者-审核者机制。如果 Reviewer 的审美偏好与目标用户不一致，比如 Reviewer 认为信息密度合理但用户觉得太拥挤，反馈循环会收敛到错误的局部最优。如何让用户的偏好反馈也参与 Reviewer 循环？**

Answer:
把用户反馈做成 Reviewer 的校准源，而不是让用户变成每轮审批的瓶颈。
- 显式反馈入口：每次迭代出低成本预览——缩略图或关键页，用户点选太挤、合适、太松，标签直接进 Reviewer 评估维度。
- 隐式信号回收：用户对成品的自行修改——自己删了一页、改了字号——是最真实的偏好，回灌为校准数据。
- 偏好参数化：信息密度等审美维度做成 Reviewer 的可调参数，由历史反馈回归出该用户的参数值，而非写死在提示词里。
- 抽样反馈不全量：循环内仍由 Reviewer 自动收敛，用户只在关键检查点介入——保住双 Agent 分工的速度优势。

**5. 本章展示了 Coding Agent 把经验沉淀回代码库的多种方式。如果把这些经验进一步提炼为系统提示词中的规则，规则集会随时间不断膨胀。如何对沉淀下来的规则做"垃圾回收"？为什么一次成功的代码修改还不能直接视为第九章所说的持续进化？**

Answer:
垃圾回收三招，全是第 3 章知识整理的移植：
- 规则带元数据：来源是哪次失败、时间、命中次数——长期零命中的进入清理候选。
- 定期归并：语义重复的合并、相互冲突的按新证据裁决——规则库就是知识库，同一套整理流程。
- 删除也要回归验证：清掉规则后跑基准，指标掉了就恢复——删除有测试兜底。

一次成功修改不等于进化，因为进化 = 变异加选择加保留：一次成功只是变异，它没有证明可复现、没有经独立验证、没有沉淀为版本化可回滚的资产。第 9 章的门槛是从评价过的轨迹提炼、经独立验证、可回滚地固化——三关一关都不能少。

**6. "对远程工作友好的团队往往也对 AI Agent 友好。"你所在的团队或组织，在知识文档化方面距离"AI-ready"还有多远？最大的障碍是什么？**

Answer:
用书里的代理指标自查：一个远程新人只靠代码仓库和文档，能不能独立开展工作。
- 检查清单：架构决策有没有书面记录、任务上下文在不在 issue 和 PR 描述里、部落知识有没有开发者指南、"这个要问老张"出现的频率。
- 最大障碍通常不是工具是激励：写文档不计入产出、分享知识稀释个人不可替代性——第 2 章的论断在此重复：这是组织问题先于技术问题。
- 讨论做法：组员各自给团队打分，并举一个"只存在于某个人脑里的关键知识"的真实例子——例子本身往往比分数有说服力。

**7. Simon Willison 提出了 Agent 的"致命三要素"（访问私有数据、暴露于不受信任内容、具备外部通信能力），本章在此基础上增加了第四个——持久记忆。在一个需要同时处理这四种要素的生产环境中，你会如何设计安全策略？**

Answer:
逐要素设防，要素之间断链——目标不是每层绝对安全，而是让同时集齐四要素的成本趋近无限。
- 数据边界：凭证不进沙盒、源码只读挂载、行级安全兜底——本章的数据层下沉。
- 输入信任边界：外部内容来源标注、隔离渲染——第 2 章；持久记忆的写入走与外部内容同等的信任审查——这是第四要素的关键防线，防指令潜伏进 MEMORY.md。
- 输出影响边界：网络出口白名单代理、Sidecar 结构化复核、不可逆操作人工确认——第 4 章。
- 跨会话边界：记忆写入审计、git 可回滚、读取时标注来源和时间、老记忆降权。
- 断链思维：单看任何一层都可被穿透，安全设计做的是每层抬一次攻击成本——四层叠加后完整攻击链的概率成本高到不划算。

**8. Artifact 模式让 Agent 生成 SQL 或前端代码，由数据库和浏览器直接执行，绕过 LLM 处理大量数据。与传统的"Agent 直接给出答案"相比，这种"Agent 生成代码、系统执行代码"的分工有什么优劣？生成的 SQL 可能执行破坏性操作、生成的 HTML 可能包含漏洞，又该如何确保安全？**

Answer:
优势：
- 绕过 LLM 中间人——数据从库直达界面，模型不抄写就不会抄错，token 省得多、延迟低。
- 代码是显式可审查产物——SQL 可以先 EXPLAIN 预演，出错可定位到具体语句。

劣势：
- 责任转移——错误从模型说错变成代码做错，爆炸半径更大；生成代码本身可能带漏洞；调试链路变长。

安全用书里的原方案：
- SQL：只读账号加语句白名单——仅批准的 SELECT、拒绝 DDL DML 多语句；用户值服务端参数化绑定；限制行数、时限、可访问表和时间范围。
- HTML：A2UI 声明式组件——只能点菜单不能进厨房；或沙盒渲染加内容安全策略。
- 两个 artifact 都在隔离环境执行、产出格式受控——Artifact 模式缩短数据路径，但不能替代权限检查与执行隔离。

**9. 将业务规则编码为工具内部基于数据库真值的校验，并用参数设计引导模型在调用前核对政策条件，本质上是用代码结构来约束 Agent 行为。这种"代码即规则"的模式相比自然语言规则有什么优势和局限？**

Answer:
优势：
- 无歧义可执行——相同输入必产生相同输出；复杂布尔组合、时间计算天然精确。
- 守门员建立在模型无法伪造的数据上——政策事实一律查库、时间用服务端时钟；独立性不仅是独立模型，更是独立数据来源。
- 可测试可审计——规则本身能进测试套件。

局限：
- 表达不了价值判断——合理、紧急这类裁量仍要自然语言留给模型；规则枚举不完，长尾场景会漏过去。
- 代码也会错——规则 bug 是系统性拒绝或放行，且更难被发现，没人怀疑机器算的；需要规则版本管理加 mismatch 日志审计。
- 僵化——政策变了要改代码发版，慢于改提示词。

所以是双轨制：提示词的自然语言规则管理解、解释和变通，代码化校验管底线——前两重减少错误发生，第三重确保错误不变成不可逆损失。
