# 第一章学习笔记：AI Agent 入门

## 1. 总结

- Agent = LLM + 上下文 + 工具（大脑/眼睛/手脚）；环境不属于 Agent。模型固定时，扩展观察/动作空间是最大的能力杠杆
- 上下文 = 静态前缀（系统提示+工具定义）+ 轨迹（历史消息），缺一不可
- ReAct：想→做→看 循环，直到没有工具调用
- 生产竞争力在 Harness：约束、验证、纠正 > 上下文、工具本身

```
Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment
```

- 从工作流到自主 Agent：先优化提示词，再考虑工作流，最后才引入自主 Agent——这是降低意外风险最实用的顺序。每种编排模式都有其适用场景，不存在通用最优解
- 安全是架构问题：护栏、人工干预、对齐（alignment，即让模型的行为与人类意图保持一致）——安全问题从第一行代码就要考虑，而不是上线前打补丁。安全问题贯穿模型、上下文、工具、协作和社会五个层面

## 2. 实验

### 2.1 实验一（消融实验）
论证 LLM 每次推理前收到的上下文由五部分组成：系统提示词、工具定义、用户消息、模型回复、工具执行结果。
消融实验：上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。

### 2.2 实验二（Kimi K3）
论证"模型即 Agent"新范式：模型变强，用工具的决策内化——"不教也会"自主调用工具，展现 Agentic 能力。

### 2.3 实验三（GPT-5.6 Deep Research）
论证先进模型把多工具研究编排也内化：搜索、读、写代码分析的循环在服务端闭环，还会先澄清意图再动手。

## 3. 思考题

**1. 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文、还是更多的工具——你会选哪个？在什么条件下你的选择会改变？**

Answer:
默认选上下文，因为它是唯一零成本复制的杠杆。
- 实验 1-1 就是证据：模型、工具都没变，只变上下文，Agent 从 3 轮干对变成编瞎话干错。上下文是收益弹性最大的一项。
- 另两项的短板：更强的模型天花板高，但贵，而且你改不动。更多的工具边际收益递减，工具一多反而选错。
- 什么时候换选择：任务答案模型根本不会，比如实验 1-2 那种训练截止日期之后的时事题，换模型。任务缺硬能力，不能联网、不能算，加工具。任务模型会但做不稳，补上下文。

**2. ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？**

Answer:
根源是每轮重读全部历史——第 i 轮读 i 条，累计约 N²/2。要么少读，要么让历史变小。
- 压轮数：并行工具调用，3 个独立换汇挤同一轮，N 从 6 变 3。
- 压新增：工具输出瘦身、状态写文件只留指针，每条消息会被重读 N 次，瘦一条赚 N 次。
- 保前缀：静态部分别动，缓存才能命中，命中约 1 折但不是免费。
- 换形状：历史压缩成摘要，或子 Agent 只带结论回来——二次方降成常数或线性，代价是改动点之后缓存作废。

**3. "模型即 Agent"范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？**

Answer:
不矛盾——模型内化的是"干活"，没人替你扛"验收"。
- 分工上移，不是消失：模型吃掉了决策，何时调、调哪个；Harness 退到治理层，管约束、验证、纠正。
- 自主性放大爆炸半径：能连调 200 次工具的模型，错了就是 200 步连环错。模型自主加上没有验证，等于自信地交出一份数字全错的报告。我们实验 1-1 里 glm-5.3 编假汇率就是现场例子。
- 实证：LangChain 从 52.8% 提到 66.5%，模型没换，提分三招是自动检查结果、检测死循环、优化策略，全是治理层代码。
- 框架未来价值四件事：权限与沙盒、验证与评估、可观测性、多模型可移植性。编排管道谁都会写且正在被 API 内置，值钱的全在治理。

**4. 消融实验中"工具结果反馈"的缺失导致 Agent 陷入无限循环。在生产环境中，除了工具结果缺失，还有哪些情况可能导致 Agent 无限循环？你会设计怎样的检测和终止机制？**

Answer:
循环的共性是——模型看不到自己在重复，或看到了也不知道怎么改。
五种成因：
- 错误信息没用：工具报错但模型不知道怎么改，原样重发。
- 状态永不变：轮询一个永远不会出现的条件，等文件、等接口返回特定值。
- 上下文太长失忆：做过的事被淹没，从头再来，等于生产版 no_history。
- Agent 互相踢皮球：A 委托 B，B 委托回 A。
- 修复逻辑本身错了：模型坚信再试一次就好。

检测和终止四件套：
- 签名去重：工具名加参数查重，K 次相同调用即报警。我们实验里的 repeated_tool_calls 就是雏形。
- 三重预算上限：迭代数、token 和费用、时钟，任一触顶即停。
- 状态不变检测：连续 N 个动作后世界没变化，强制升级。
- 独立监控器：旁观进程盯轨迹，发现循环后注入"你在重复"的提示、强制摘要、或转人工。LangChain 提分靠的就是这招。

**5. 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？**

Answer:
拿 Claude Code 做示范。
- 感知：读文件、搜索结果、IDE 状态、图片。拉取式——自己决定看什么，开放。
- 行动：跑命令、改文件、联网。动作开放，但套着权限系统，每步可拦截，是开放动作加受控执行的组合。
- 策略：LLM 主导决策，用计划模式、待办列表、memory 文件约束长程行为。

合理之处：动作开放才接得住长尾任务，权限层兜住不可逆操作。
改进空间：循环检测和长任务的上下文管理仍是痛点，正好呼应第 2、4 题。

**6. 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？**

Answer:
主干用工作流，例外用 Agent，混合是标准答案。
- 主干归工作流：查询、比价、确认、支付是确定性流程，要幂等、可审计、可回滚，工作流的天下。
- 两处需要 Agent：入口的意图理解，用户说"我妈腿脚不便帮我安排靠过道"，工作流枚举不全。异常时的重规划，航班取消要在约束下重新组合方案。
- 混合模式：Agent 管判断，工作流管交易。Agent 输出结构化意图，工作流执行出票退款；金额设上限，超限转人工。

**7. 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？**

Answer:
风险不是工具的属性，是工具、参数、上下文三者的函数。

核心公式：
```
风险 = 工具基线 × 参数因子 × 环境因子

delete_file("/tmp/foo.txt")           低 × 1   × 测试环境 → 放行
delete_file("C:/Windows/system32/x")  低 × 10  × 生产     → 拒绝
delete_file("~", recursive=True)      低 × 100 × 任意     → 拒绝并告警
```

分层实现：
- 参数层硬约束：路径黑白名单，系统目录、通配符、递归标志各自是独立的风险因子。
- 上下文层加权：当前目录、生产还是开发环境、用户角色、影响面，删一个文件还是删一个目录树。
- 处置分级：按风险阈值自动放行、要求人工确认并展示预览、直接拒绝。
- 兜底：可逆化设计，回收站代替删除；限速；审计日志。

现实参照：Claude Code 的权限系统就是活实现——读文件自动放行、改文件逐个确认、命令按白名单分级。

**8. 本章的 Agent 产品表格中，所有 Agent 的动作空间都是"开放式"的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？**

Answer:
当正确行为可枚举、且错误代价不可逆时。
- 高危领域：支付、医疗、航空，接第 6 题。流程可枚举、错误代价高，预定义选项即工作流。
- 要审计合规：受限空间每一步可测试、可回放、可追责。
- 成本与延迟：小模型也能可靠驱动，不需要强模型的全域判断。
- 用户要可预期：客服流程要的是确定性，不要每次不一样的创意。

开放式的价值在长尾：没枚举到的请求。所以成熟产品的形态是受限核心加开放兜底——枚举内走菜单，枚举外升级到 LLM 或人工。

**9. 人工干预机制要求 Agent 能"优雅地移交控制"。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？**

Answer:
把问人当成一次工具调用，而人是慢、贵、不可靠的工具——就该有超时、兜底和降级，和其他工具一模一样。
四件套：
- 超时加安全默认值：每个待确认事项预定义没人响应时怎么办，默认永远在保守侧——付款确认超时即取消，绝不能默认视为同意。不可逆动作等待，可逆动作继续。
- 异步挂起不阻塞：任务停机坪状态并持久化上下文，人上线后从断点恢复。等的时候先把可逆部分全做完，把需要人的窗口压缩到只剩最后一下提交。
- 升级阶梯：用户、备用审批人、带护栏的自动处置、终止并报告，逐级下探。
- 模糊指令处置：问一次、给具体选项，不开放式提问，实验 1-3 的意图澄清就是这个范式。人联系不上就取最保守解读，显式记录假设，只执行可撤销部分，模糊部分挂起。

现实参照：Claude Code 交互场景逐个确认，人走开就等；后台任务根本不问，改成预先划定权限范围再跑。

**10. 引言指出"好的设计原则应该穿越模型的迭代周期"，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。**

Answer:
手段会死，原则不死——模型内化的是能力，Harness 保留的是责任。
- 例一：显式思维链提示。我们 agent.py 的系统提示词还写着"一步步想并按需用工具"，这是 CoT 时代的标准咒语。原则是给模型决策提供结构，永远成立；但实验 1-2 的 K3 常开思考模式，推理已内化，再命令它一步步想不但多余，甚至干扰。这条咒语是活化石。
- 例二：输出格式防御工事。execute_task 里有一整套工具参数 JSON 非法就保住本轮、回写错误让模型重试的逻辑。原则是接口边界必须校验，永远成立；但实验 1-3 展示了原生结构化输出，当模型侧可靠保证格式合法，这整段防御就成了死代码。

为什么手段死、原则不死：能力被模型内化后，旧手段死了；但"结果要可靠"的责任没人替你扛——校验只是从客户端挪走，升级成实验 1-3 那种独立参照和防吹牛条款。

清醒剂：手段的拆除必须以证据为前提，不能以宣传为前提。那个 JSON 防御存在是因为真有模型在那里翻过车。判断过时的唯一标准是失败率证据。渐进拆除、留好回滚——这本身就是 Harness 原则用在 Harness 自己身上。
